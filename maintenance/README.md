# Exact reviewed scoped maintenance entry

This replaces the diagnostic-only wrapper only after the exact code/config review. It is not a deployment or permission issuer. Global execution, scan scheduler, automatic content sync and V1 worker remain off. Runtime confirmation still uses the original authenticated administrator UI and original claim transaction.

`unified-start.mjs` itself reads `PUBLISHER_REVIEWED_RELEASE_SPEC` and `PUBLISHER_SCOPED_AUTHORIZATION_FILE`; setting the latter on the old wrapper is insufficient. Both must be absolute, regular, nonsymlink mode-0600 files. The reviewed release spec fixes the exact Git SHA, release directory ending in that SHA, and original database path. The wrapper requires all three original global flags to be `0`, validates the account/actor/Business Page/profile binding and optional original diagnostic snapshot, acquires the original service lock, composes the app with `scopeAuthorization`, and listens only on 127.0.0.1:17882. It does not start V1 or any batch worker.

The private scoped config is `{version:1, scopeAuthorization:{...}, targets:[...]}`. `scopeAuthorization` requires the explicit real workspace/account/actor/Page/profile, operations, a separately approved future `expires_at` in milliseconds (at most 24 hours, not a generated default), auditable original approval references, and complete read-only legacy history. A V1 source needs the actual SQLite database plus two distinct JSONL paths and the YAML ledger; no `additional_history:[]`, no missing/corrupt schema or mirror. All files are read in isolated tests only during this engineering task. No production config is written by the package.

Each target is `{kind:PAGE|GROUP|INTERACTION,id:<existing actual task/post ID>,scope_hash:<complete reconstructed SHA256>}`. INTERACTION also supplies the exact reviewed `reply_body` so startup can reconstruct its hash; the final UI must submit the same body. Optional `snapshot_hash` on a Page target adds only that existing task's approve route. Targets are also propagated into the core policy as `approved_targets`, so an unselected task's capability is denied, not merely its HTTP execute request. Startup recomputes every target and verifies profile/full scope before listening. For a new DRAFT image Page with exact snapshot_hash, startup and its approve route validate the approved source bytes under the trusted customer root. Only the original UI /approve freezes media; the executor rechecks the resulting immutable asset scope before promoting to READY. Normal capability/execute still require frozen assets and READY. No startup approval, permit, or driver invocation occurs. Consumed/attempted tasks cannot use this preparation scope. The new-DRAFT actual wrapper UI journey is covered by test/scoped-image-approval-ui.test.js without test preapproval.

Finite POST routes for those exact IDs:

- `/auth/login` retains original Origin/login checks.
- `/api/unified/workspaces/<ws>/jobs/<explicit Page ID>/execute`, and optionally that ID's `/approve` with exact snapshot hash.
- `/api/workspaces/<ws>/group-jobs/<explicit group job ID>/execution-capability`.
- `/api/workspaces/<ws>/group-jobs/auto-publish` requires exactly one enumerated job, current hash and explicit rules acknowledgment.
- `/api/workspaces/<ws>/proactive/posts/<explicit post ID>/execution-capability` and `/execute`, with the exact full reviewed reply/action scope.
- Original unified and Facebook `accounts/select` accept only the bound account ID; no account/profile modification.
- Optional one original UNKNOWN diagnostics route, independently bound to its unchanged full snapshot, with original diagnostic semantics and no execute/reconcile/reset allowance.

GET/static behavior retains the existing wrapper reads and adds only `/scoped-confirmation-ui.js`. Every forwarded request still passes the original Host/admin authentication, Origin/CSRF and application-token authorization. `requestGuard` runs after those checks and parsed JSON, rejecting extra fields, unknown IDs, altered scope, multi-job batches, other customer/account/profile and expiry. There is no stream-body replay, invented login or token-based substitute.

The execution window enables **existing explicitly reviewed tasks**, not general task/content/group creation. An optional separate `preparations` configuration opens only exact Page/group preview creation, never automatically enumerates the resulting IDs for execution. No wildcard POST or new-task auto-enumeration. The normal original Page task, group job and proactive candidate controls are exercised through this exact composition in `test/scoped-wrapper-ui.test.js`. The original full create/preview/confirm journeys remain tested in `test/scoped-ui-journey.test.js`. If production does not yet have the explicitly selected NEW task/candidate IDs, the execution config cannot be activated: use the implemented, separately reviewed exact non-platform `preparations` allowance in the original UI, then bind the resulting actual IDs/hash before the execution-window switch. PAGE preparation freezes content ID/hash, exact title/body/tags/author payload, body hash and ordered actual media hashes. GROUP preparation freezes one content ID/hash/full body/media and at most two explicit existing joined group IDs/external IDs/URLs. It accepts no content/account/profile/group mutation or scan. A preparation-only config has `targets:[]`; created DRAFT/PENDING objects have no capability/execute authority and issue no permits. Full authenticated creation and wrong-body/target/execute rejection are isolated-test verified. Do not recreate UNKNOWN, mint a parallel job to avoid history, or expand route prefixes. This is an explicit scope prerequisite rather than an unimplemented hidden runtime exception.

Production inputs must be settled before deployment: new job/post IDs and hashes, exact profile, independently approved expiry/source references, original read-only history paths, and whether the original diagnostic remains valid. The review pack's template deliberately has invalid placeholders and is not live authority. No policy or permit is issued during engineering. Once all inputs are reviewed, fill only those values; deploy the exact reviewed wrapper files/release spec in one idle window, preserve the original Chrome and lease, and compare historical DB/audit tables byte-for-byte. New empty scoped tables do not authorize a retry. The first upgrade to the separately approved seven-day persistent session implementation needs normal login once; later restarts retain only unexpired sessions. See docs/browser-session-persistence.md.

Validation uses the same `createControlledApp` module as production, real temporary SQLite, actual localhost HTTP and new isolated Chrome, existing app auth/CSRF, mock platform drivers, blocked external requests. Missing history/bad file modes/symlinks/SHA/flags, auth/CSRF/app-token denial, exact target/account/customer boundaries and queue denial are tested. Existing restart tests retain spent Page/group/interaction attempts; the wrapper suite adds exact boundary checks and three actual UI journeys with cancellation and double-click behavior. No live platform/profile validation is claimed.


## Default zero-authorization startup

If PUBLISHER_SCOPED_AUTHORIZATION_FILE is absent (not an empty string, bad file, empty policy or placeholder), unified-start selects READ_ONLY without synthesizing authority. It may preserve only the existing private PUBLISHER_READONLY_DIAGNOSTIC_CONFIG descriptor: exact original UNKNOWN job/workspace/account/content/snapshot/actor/Page/FB-BROWSER/media binding is verified before listening and before each authenticated CSRF-protected diagnostic POST. GET report remains available. Wrong binding/path/hash/extra fields are rejected. No diagnostic is started by boot or by deployment.

In READ_ONLY the shared composition disables global execution/scheduler/automatic sync, creates no ScopedOperations adapter, does not run startup task/diagnostic recovery, and admits only normal login, existing read/static routes (including scoped-confirmation-ui.js) and that one exact diagnostic POST. Every create/prepare/approve/execute/grant/reconcile/reset/queue/account-selection/settings route stays denied, even if a legacy AVAILABLE permit exists. Original platform diagnostic semantics remain read-only and never authorize retry. Headers identify read-only rather than scoped-task-confirmation mode. The zero-authority branch never grants publishing rights or changes network security. The separately user-approved seven-day session implementation is documented in docs/browser-session-persistence.md; normal authenticated CSRF-protected logout is allowed solely for revocation.

Invalid supplied scoped files fail startup; they are never downgraded to READ_ONLY. A later actual scoped configuration still must satisfy the original exact policy/history/targets/preparations requirements and original final-confirmation/claim path. No config hot reload, automatic ID enumeration or new privileges are added. Missing scope is sufficient to deploy useful read-only UI and the preserved 009 diagnostic; it is not authority to use prepare/approve or issue a task permit.
