# V3 → Mac execution relay (dormant candidate)

This candidate adds a job-specific relay in the authenticated Mac unified service. It is **off by default** (`PUBLISHER_ENABLE_V3_BRIDGE` is absent in production). No Site route, token, binding, customer account, media upload, or live publication was created by this change. The hosted Site still reports `external_upload` and `publish` unavailable. Tests of this relay are synthetic and do not count as platform publication.

## Proven boundary

- Only the existing authenticated Mac unified service can instantiate the relay. It uses the same `UnifiedPublisher` and `UnifiedExecutor` as the normal Mac UI. Thus the local account and profile checks, current content and media freeze, V1/V2 history checks, quota/permit checks, submit intent, UNKNOWN protection, and driver readback remain authoritative.
- An existing Publisher admin must approve **one** V3 Site job/workspace/account/snapshot/QA/manifest tuple; `prepare` alone creates the corresponding local job binding after all checks. The old standalone bind route returns `V3_LEGACY_BIND_DISABLED`. The local content must first have an exact `publisher_content_sources` import row with `source_id=sites:<project>:<site-job>` and `revision=<site-snapshot-hash>`; an unrelated old V2 job cannot be bound. Preparation is idempotent; a second local or Site job mapping is rejected. The Site job ID alone grants no permission.
- A new, time limited Publisher app token would need one local workspace, exact Site job IDs, and only the specific required `v3:status`, `v3:upload`, `v3:prepare`, `v3:dispatch`, and/or `v3:reconcile` scopes. Existing tokens retain their old permissions. No production token has been minted.
- `GET /api/v3-bridge/jobs/:siteJobId/status` returns local task state and attempt ID. Platform ID/URL and `verified:true` appear only after the native executor's verified `PUBLISHED` or `PUBLISHED_ID_PENDING` terminal readback, with evidence origin and selected content/media hashes. A submit receipt while UNKNOWN is only `pending_receipt:true`; a WeChat `DRAFT_WRITTEN` is only `draft_verified:true`, never published. `GET .../capability` reads the original local executor preflight. `POST .../dispatch` requires both exact snapshot hashes and confirmation; it only calls the existing executor when the local task is READY and local task approval remains active. A repeated call after PREPARING/SUBMITTING/UNKNOWN returns status without resubmission. `POST .../reconcile` delegates to the original readback path only for UNKNOWN. The former direct bind operation is disabled; app-token operations cannot invoke it.
- `src/sites/mac-execution-relay-client.js` is a server-only HTTPS client with a fixed Publisher hostname, exact job URL, bounded JSON readback and no redirect. A transport failure returns `V3_RELAY_OUTCOME_UNKNOWN`; the caller must read status before any further action. It is not yet wired into the public Site handler.
- `POST /api/v3-bridge/jobs/:siteJobId/media/:ordinal` accepts a bounded binary stream only from a token with exact `v3:upload` scope. It checks declared length, SHA-256, signature and MIME, writes an atomic private file, and returns no local path. Exact repeated bytes are idempotent; conflicting bytes fail. This is **staging only**, not an approved media manifest or a native Publisher import.
- Admin-only `POST /api/v3-bridge/account-bind` stores an exact Sites workspace/account → local workspace/account mapping after re-reading the local platform and external identity. A Page public profile ID cannot silently stand in for a Business asset ID. Admin-only `POST /api/v3-bridge/task-approve` binds one Site job, snapshot, QA receipt and full platform/media manifest digest; the same job cannot be approved for changed bytes or text. Admin-only `POST /api/v3-bridge/task-revoke` prevents future dispatch but cannot undo a platform action already in flight, which must be reconciled. `POST /api/v3-bridge/jobs/:siteJobId/prepare` requires both active admin records, the exact Site snapshot, ordered staged media with renewed hash checks, and a token scoped to that local workspace and Site job. It uses the original local content import, job creation, media freeze and approval, then binds the task. It does **not** submit to any platform.
- The relay does not raise a daily limit or turn on `PUBLISHER_ENABLE_EXECUTION`, scan, sync, or any platform driver. Current Mac Page execution is separately restricted to its configured account and operating day.

## Required before activation and real acceptance

1. Verify the existing `publisher.vietbridge.one` route really reaches this Mac service over the current authenticated tunnel, then confirm its exact HTTPS origin and readback. Do not open a new public port or change Cloudflare/VPN just to activate the relay.
2. Implement a **trusted Sites server-side** operation that checks official ChatGPT identity, membership, exact account, approved production source, QA, current frozen snapshot, and a fresh deliberate publish confirmation before calling the relay. Never expose the bearer token to the browser. The current Site's synthetic approval and upload classes do not authorize real media or dispatch.
3. Wire the new binary staging route and native prepare endpoint to the Site's **approved R2 objects and immutable QA receipt**. The Mac side now rechecks ordered staged objects and imports a local job, but the hosted Site does not yet have a real producer/review source or a trusted server-side route that verifies that receipt. The local admin must first confirm the exact account mapping and reviewed task/manifest; no records were added in production. A client-supplied QA hash alone is never proof of review. The current Site draft task has `media:[]`, so a text-only bridge binding must not be presented as image publication readiness. Map an existing *verified* local account and profile to the Sites customer; do not equate Facebook public profile IDs with Business asset IDs.
4. Establish the same **local** task as the authoritative job for all entry points. The Site database should cache state/receipts, not allocate independent quota. Reconcile existing UNKNOWN and history before creating each task; check platform history for duplicates. Admin binding of a preexisting V2 job alone is not proof that V3 originated/imported the content.
5. Only after (1)-(4), create an exact, short lived token through the existing admin flow, store it in the Site's server-only secret binding, enable the Mac relay flag with a backed-up rollback plan, and verify one real approved case at a time. Revoke via the existing `/api/access/tokens/revoke`, remove Site secret, and disable the relay flag to roll back. No client cookie, password, Chrome profile, or platform credential needs to be copied to Sites.

The new credential and server-only secret binding are persistent security changes. Seek action-time approval for **one token scoped to named Site task IDs and one local workspace, at most seven days**, and the Site-to-existing-Mac HTTPS call. No approval is needed to keep developing and testing code while the relay remains off. Formal WeChat publishing remains unsupported by the current native adapter, which only verifies `DRAFT_WRITTEN`; that platform cannot be claimed complete from a draft.
