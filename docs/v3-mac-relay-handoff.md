# V3 → Mac execution relay (dormant candidate)

This candidate adds a job-specific relay in the authenticated Mac unified service. It is **off by default** (`PUBLISHER_ENABLE_V3_BRIDGE` is absent in production). It also adds candidate Sites routes, a migration and a visible manual-review flow, but these have not been deployed to hosted D1/R2. No token, account binding, live media upload or platform publication was created. Tests are synthetic and do not count as platform publication.

## Proven boundary

- Only the existing authenticated Mac unified service can instantiate the relay. It uses the same `UnifiedPublisher` and `UnifiedExecutor` as the normal Mac UI. Thus the local account and profile checks, current content and media freeze, V1/V2 history checks, quota/permit checks, submit intent, UNKNOWN protection, and driver readback remain authoritative.
- An existing Publisher admin must approve **one** V3 Site job/workspace/account/snapshot/QA/manifest tuple. Only `prepare` can create the local binding after the exact checks; the former standalone bind route is disabled. The local content must have an exact `publisher_content_sources` import row with `source_id=sites:<project>:<site-job>` and `revision=<site-snapshot-hash>`; an unrelated old V2 job cannot be bound. The Site job ID alone grants no permission.
- A new, time limited Publisher app token would need one local workspace, exact Site job IDs, and only the specific required `v3:status`, `v3:upload`, `v3:prepare`, `v3:dispatch`, and/or `v3:reconcile` scopes. Existing tokens retain their old permissions. No production token has been minted.
- `GET /api/v3-bridge/jobs/:siteJobId/status` returns local task state and attempt ID. Platform ID/URL and `verified:true` appear only after the native executor's verified non-synthetic `PUBLISHED` or `PUBLISHED_ID_PENDING` terminal readback with its frozen snapshot. A submit receipt while UNKNOWN is only `pending_receipt:true`; a WeChat `DRAFT_WRITTEN` is only `draft_verified:true`, never published. `GET .../capability` reads the original local executor preflight. `POST .../dispatch` requires both exact snapshot hashes and confirmation; it only calls the existing executor when the local task is READY and local task approval remains active. A repeated call after PREPARING/SUBMITTING/UNKNOWN returns status without resubmission. `POST .../reconcile` delegates to the original readback path only for UNKNOWN. Direct `POST /api/v3-bridge/bind` returns `V3_LEGACY_BIND_DISABLED`.
- `src/sites/mac-execution-relay-client.js` is a server-only HTTPS client with a fixed Publisher hostname, exact job URL, bounded JSON readback and no redirect. A transport failure returns `V3_RELAY_OUTCOME_UNKNOWN`; the caller must read status before any further action. `src/sites/worker-entry.js` constructs it only when the server-only enable flag and secret are supplied; production has neither.
- `POST /api/v3-bridge/jobs/:siteJobId/media/:ordinal` accepts a bounded binary stream only from a token with exact `v3:upload` scope. It checks declared length, SHA-256, signature and MIME, writes an atomic private file, and returns no local path. Exact repeated bytes are idempotent; conflicting bytes fail. This is **staging only**, not an approved media manifest or a native Publisher import.
- Admin-only `POST /api/v3-bridge/account-bind` stores an exact Sites workspace/account → local workspace/account mapping after re-reading the local platform and external identity. A Page public profile ID cannot silently stand in for a Business asset ID. Admin-only `POST /api/v3-bridge/task-approve` binds one Site job, snapshot, QA receipt and full platform/media manifest digest; the same job cannot be approved for changed bytes or text. Admin-only `POST /api/v3-bridge/task-revoke` prevents future dispatch but cannot undo a platform action already in flight, which must be reconciled. `POST /api/v3-bridge/jobs/:siteJobId/prepare` requires both active admin records, the exact Site snapshot, ordered staged media with renewed hash checks, and a token scoped to that local workspace and Site job. It uses the original local content import, job creation, media freeze and approval, then binds the task. It does **not** submit to any platform.
- The relay does not raise a daily limit or turn on `PUBLISHER_ENABLE_EXECUTION`, scan, sync, or any platform driver. Current Mac Page execution is separately restricted to its configured account and operating day.

## Required before activation and real acceptance

The candidate `0012_real_publish_candidate.sql`, `real-publication.js`, and `/real-contents` and `/real-jobs` endpoints provide owner-scoped R2 byte/SHA upload, ordered preview, explicit manual QA with source URLs, immutable real task freeze, Site prepare/submit intent, Mac relay calls, UNKNOWN readback and a Workbench UI. `OWNER_MANUAL_REVIEW` is an auditable human assertion, **not** a claim that model research or independent factual inspection passed. The new routes are separate from synthetic review records. The Site does not allocate a platform quota. The migration is not registered or applied on the hosted Site; the real relay flag is still off.

1. Verify the existing `publisher.vietbridge.one` route really reaches this Mac service over the current authenticated tunnel, then confirm its exact HTTPS origin and readback. Do not open a new public port or change Cloudflare/VPN just to activate the relay.
2. Use the official Sites starter to register and apply migration 0012 with a backup; verify official ChatGPT identity, membership and isolated R2 binding on hosted D1. The candidate only records owner manual checks and source URLs; a real article still requires review of actual facts, rights, language and each image before confirming. Never treat the old synthetic approval or `MANUAL_UNVERIFIED` tag alone as production QA.
3. Verify that Site R2 object SHA/ordered media, owner QA receipt, frozen snapshot and Mac local admin approval all refer to the same actual account and content. The local admin must confirm the exact account mapping and reviewed task/manifest; no records were added in production. A client-supplied QA hash alone is never proof of review. Map an existing *verified* local account and profile to the Sites customer; do not equate Facebook public profile IDs with Business asset IDs.
4. Establish the same **local** task as the authoritative job for all entry points. The Site database should cache state/receipts, not allocate independent quota. Reconcile existing UNKNOWN and history before creating each task; check platform history for duplicates. Admin binding of a preexisting V2 job alone is not proof that V3 originated/imported the content.
5. Only after (1)-(4), create an exact, short lived token through the existing admin flow, store it in the Site's server-only secret binding, enable the Mac relay flag with a backed-up rollback plan, and verify one real approved case at a time. Revoke via the existing `/api/access/tokens/revoke`, remove Site secret, and disable the relay flag to roll back. No client cookie, password, Chrome profile, or platform credential needs to be copied to Sites.

The new credential and server-only secret binding are persistent security changes. Seek action-time approval for **one token scoped to named Site task IDs and one local workspace, preferably one day**, and the Site-to-existing-Mac HTTPS call. No approval is needed to keep developing and testing code while the relay remains off. Formal WeChat publishing remains unsupported by the current native adapter, which only verifies `DRAFT_WRITTEN`; that platform cannot be claimed complete from a draft.
