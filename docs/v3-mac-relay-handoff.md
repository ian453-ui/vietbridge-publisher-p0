# V3 → Mac execution relay (dormant candidate)

This candidate adds a job-specific relay in the authenticated Mac unified service. It is **off by default** (`PUBLISHER_ENABLE_V3_BRIDGE` is absent in production). No Site route, token, binding, customer account, media upload, or live publication was created by this change. The hosted Site still reports `external_upload` and `publish` unavailable. Tests of this relay are synthetic and do not count as platform publication.

## Proven boundary

- Only the existing authenticated Mac unified service can instantiate the relay. It uses the same `UnifiedPublisher` and `UnifiedExecutor` as the normal Mac UI. Thus the local account and profile checks, current content and media freeze, V1/V2 history checks, quota/permit checks, submit intent, UNKNOWN protection, and driver readback remain authoritative.
- An existing Publisher admin must bind **one** V3 Site project/job/workspace/account/snapshot hash to **one** local workspace/account/job/snapshot hash. Bind is idempotent; a second local or Site job mapping is rejected. The Site job ID alone grants no permission.
- A new, time limited Publisher app token would need one local workspace, exact Site job IDs, and only `v3:status`, `v3:dispatch`, and/or `v3:reconcile`. Existing tokens retain their old permissions. No token has been minted.
- `GET /api/v3-bridge/jobs/:siteJobId/status` returns local task state, attempt ID, and available receipt/readback identifiers. `GET .../capability` reads the original local executor preflight. `POST .../dispatch` requires both exact snapshot hashes and confirmation; it only calls the existing executor when the local task is READY. A repeated call after PREPARING/SUBMITTING/UNKNOWN returns status without resubmission. `POST .../reconcile` delegates to the original readback path only for UNKNOWN. Admin-only `POST /api/v3-bridge/bind` is separate from app-token operations.
- The relay does not raise a daily limit or turn on `PUBLISHER_ENABLE_EXECUTION`, scan, sync, or any platform driver. Current Mac Page execution is separately restricted to its configured account and operating day.

## Required before activation and real acceptance

1. Verify the existing `publisher.vietbridge.one` route really reaches this Mac service over the current authenticated tunnel, then confirm its exact HTTPS origin and readback. Do not open a new public port or change Cloudflare/VPN just to activate the relay.
2. Implement a **trusted Sites server-side** operation that checks official ChatGPT identity, membership, exact account, approved production source, QA, current frozen snapshot, and a fresh deliberate publish confirmation before calling the relay. Never expose the bearer token to the browser. The current Site's synthetic approval and upload classes do not authorize real media or dispatch.
3. Add normal R2-to-Mac media transfer with per-object byte length, SHA-256, MIME, ordered manifest, bounded size, private local staging, and a re-read against the approved Site snapshot. The current Site draft task has `media:[]`, so a text-only bridge binding must not be presented as image publication readiness. Map an existing *verified* local account and profile to the Sites customer; do not equate Facebook public profile IDs with Business asset IDs.
4. Establish the same **local** task as the authoritative job for all entry points. The Site database should cache state/receipts, not allocate independent quota. Reconcile existing UNKNOWN and history before creating each task; check platform history for duplicates. Admin binding of a preexisting V2 job alone is not proof that V3 originated/imported the content.
5. Only after (1)-(4), create an exact, short lived token through the existing admin flow, store it in the Site's server-only secret binding, enable the Mac relay flag with a backed-up rollback plan, and verify one real approved case at a time. Revoke via the existing `/api/access/tokens/revoke`, remove Site secret, and disable the relay flag to roll back. No client cookie, password, Chrome profile, or platform credential needs to be copied to Sites.

The new credential and server-only secret binding are persistent security changes. Seek action-time approval for **one token scoped to named Site task IDs and one local workspace, at most seven days**, and the Site-to-existing-Mac HTTPS call. No approval is needed to keep developing and testing code while the relay remains off. Formal WeChat publishing remains unsupported by the current native adapter, which only verifies `DRAFT_WRITTEN`; that platform cannot be claimed complete from a draft.
